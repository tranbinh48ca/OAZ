Introduction to Oracle Database Security

Tổng quan bảo mật Oracle Database và các khái niệm cơ bản

📖Giải Thích Chi Tiết

1. Tại Sao Database Security Quan Trọng?

Database chứa tài sản quan trọng nhất của tổ chức: customer data, financial records, intellectual property, trade secrets. Vi phạm bảo mật database có thể dẫn đến:

  • Thiệt hại tài chính: Phạt vi phạm GDPR lên đến €20 triệu hoặc 4% doanh thu
  • Mất uy tín: 60% công ty bị breach phải đóng cửa trong 6 tháng
  • Tranh tụng pháp lý: Class-action lawsuits từ customers bị ảnh hưởng
  • Competitive disadvantage: Mất trade secrets cho đối thủ
THỐNG KÊ QUAN TRỌNG: • 80% data breaches liên quan đến database
• Average cost of breach: $4.24 triệu (IBM 2021)
• 95% breaches do lỗi human error hoặc misconfiguration
• Time to identify breach: 207 ngày trung bình

2. Defense in Depth Strategy

Oracle sử dụng phòng thủ nhiều lớp - nếu một lớp bị vượt qua, các lớp khác vẫn bảo vệ:

Security Layer Oracle Technology Protection Against
Network Security Native Network Encryption, TLS/SSL Eavesdropping, man-in-the-middle attacks
Authentication Password, Kerberos, PKI, RADIUS, LDAP Unauthorized access, identity theft
Authorization Privileges, Roles, VPD, Label Security Privilege escalation, unauthorized data access
Separation of Duties Database Vault Insider threats, privileged user abuse
Data Encryption TDE (Transparent Data Encryption) Data theft via OS, stolen backups/disks
Data Masking Data Masking & Subsetting Pack Exposure of sensitive data in non-prod
Auditing Unified Audit, Database Vault Audit Detecting suspicious activity, compliance

3. Common Security Threats

Top 10 Database Security Threats:
  • SQL Injection: Kẻ tấn công inject malicious SQL qua application inputs
  • Weak Authentication: Default passwords, weak policies, no MFA
  • Excessive Privileges: Users có quyền nhiều hơn cần thiết
  • Insider Threats: DBAs, developers với excessive access
  • Unpatched Vulnerabilities: Missing security patches, old versions
  • Unencrypted Data: Data at rest và in transit không mã hóa
  • Backup Exposure: Unencrypted backups stored insecurely
  • Database Link Abuse: Hopping giữa databases qua links
  • Audit Trails Disabled: Không track suspicious activities
  • Social Engineering: Phishing attacks targeting credentials

4. Oracle Security Architecture

Oracle Database được thiết kế với bảo mật tích hợp sẵn từ kernel level:

  • Mandatory Access Control (MAC): Kernel enforces security policies
  • Discretionary Access Control (DAC): Object owners grant permissions
  • Role-Based Access Control (RBAC): Permission qua roles, không direct grants
  • Virtual Private Database (VPD): Row-level security tự động
  • Oracle Label Security: Multi-level security classification
  • Database Vault: Separation of duties, trusted paths

Ví Dụ 4: Implement Row-Level Security với VPD

-- Scenario: Sales reps chỉ thấy customers của mình

-- 1. Create security policy function
CREATE OR REPLACE FUNCTION sales_territory_policy(
  p_schema VARCHAR2,
  p_object VARCHAR2
) RETURN VARCHAR2
IS
  v_user VARCHAR2(30);
  v_predicate VARCHAR2(2000);
BEGIN
  v_user := SYS_CONTEXT('USERENV', 'SESSION_USER');
  
  -- Managers see all
  IF v_user IN ('SALES_MGR', 'VP_SALES') THEN
    RETURN NULL;
  -- Reps see only their territory
  ELSE
    v_predicate := 'sales_rep = SYS_CONTEXT(''USERENV'',''SESSION_USER'')';
    RETURN v_predicate;
  END IF;
END;
/

-- 2. Apply policy to table
BEGIN
  DBMS_RLS.ADD_POLICY(
    object_schema   => 'SALES',
    object_name     => 'CUSTOMERS',
    policy_name     => 'sales_territory_policy',
    function_schema  => 'SALES',
    policy_function => 'sales_territory_policy',
    statement_types => 'SELECT,INSERT,UPDATE,DELETE',
    policy_type     => DBMS_RLS.SHARED_CONTEXT_SENSITIVE
  );
END;
/

-- 3. Test as different users
CONNECT sales_rep1/password@db
SELECT COUNT(*) FROM sales.customers;
-- Returns only customers where sales_rep = 'SALES_REP1'

CONNECT sales_mgr/password@db
SELECT COUNT(*) FROM sales.customers;
-- Returns ALL customers
VPD LƯU Ý: VPD policies execute at SQL parse time, adding WHERE clause automatically. User KHÔNG THỂ bypass được. Performance impact minimal với function result cache. Use SHARED_CONTEXT_SENSITIVE cho best performance.

1 Giải thích Defense in Depth strategy. Tại sao cần nhiều lớp bảo vệ thay vì một lớp mạnh?
👁️ Xem Đáp Án
Defense in Depth (Phòng thủ nhiều lớp):
Là chiến lược bảo mật sử dụng nhiều lớp bảo vệ độc lập. Nếu một lớp fail, các lớp khác vẫn bảo vệ.

Các lớp trong Oracle:
1. Network Encryption - bảo vệ data in transit
2. Authentication - verify user identity
3. Authorization (Privileges/Roles/VPD) - control access
4. Database Vault - separation of duties
5. TDE - encrypt data at rest
6. Auditing - detect suspicious activity
7. Data Masking - protect non-prod data

Tại sao cần nhiều lớp:
• Không có giải pháp nào 100% hoàn hảo
• Attackers sử dụng multiple attack vectors
• Insider threats bypass network security
• Mistakes happen - misconfiguration, human error
• Compliance requires multiple controls

Ví dụ thực tế: Nếu password bị stolen (auth layer compromised), VPD vẫn restrict data access, TDE vẫn protect data nếu disks stolen, audit vẫn track suspicious queries.
2 Top 3 database security threats phổ biến nhất? Cách phòng chống?
👁️ Xem Đáp Án
1. SQL Injection Attacks:
• Threat: Attacker inject malicious SQL qua application inputs
• Prevention: Use bind variables, validate inputs, least privilege, WAF
• Oracle: VPD adds automatic WHERE clause, blocks unauthorized access

2. Insider Threats / Privileged User Abuse:
• Threat: DBAs, developers với excessive access stealing/modifying data
• Prevention: Separation of duties, Database Vault, comprehensive auditing
• Oracle: Database Vault prevents even SYS from accessing app data

3. Weak Authentication & Passwords:
• Threat: Default passwords, weak policies, no MFA, password reuse
• Prevention: Strong password policies, MFA, Kerberos/PKI authentication
• Oracle: Password verify functions, profiles, failed login tracking, account locking

Other Major Threats:
• Unpatched vulnerabilities → Regular patching schedule
• Unencrypted data → TDE for data at rest, Network Encryption
• Missing auditing → Unified Audit, Database Vault audit reports
3 So sánh Mandatory Access Control (MAC) vs Discretionary Access Control (DAC) trong Oracle?
👁️ Xem Đáp Án
Discretionary Access Control (DAC):
• Object owner controls access
• Owner grant/revoke permissions to others
• Example: Table owner grants SELECT to user
• Flexible nhưng có security risks
• Risk: Users có thể grant privileges to unauthorized users

Mandatory Access Control (MAC):
• System enforces security policies
• Users CANNOT override policies
• Security administrator controls policies
• Example: Oracle Label Security, Database Vault
• More secure cho high-security environments

Oracle Implementation:
• Standard grants/privileges = DAC
• VPD policies = MAC (users can't bypass WHERE clause)
• Label Security = MAC (sensitivity labels enforced)
• Database Vault = MAC (realms, command rules enforced)

Best Practice: Use combination - DAC for flexibility, MAC for critical security requirements. Financial data, PII should use MAC controls.
4 Compliance requirements (GDPR, HIPAA, PCI-DSS) yêu cầu những security controls gì trong Oracle?
👁️ Xem Đáp Án
GDPR (General Data Protection Regulation):
• Data encryption at rest và in transit → TDE, Network Encryption
• Access controls và audit trails → Privileges, Unified Audit
• Data minimization → Data Masking for test environments
• Right to be forgotten → Data deletion capabilities
• Breach notification (72 hours) → Comprehensive monitoring

HIPAA (Health Insurance Portability):
• Encrypt PHI (Protected Health Information) → TDE
• Access controls → Role-based access, VPD
• Audit trails → Who accessed what patient data when
• Automatic logoff → Profile IDLE_TIME setting
• Emergency access procedures → Break-glass accounts

PCI-DSS (Payment Card Industry):
• Encrypt cardholder data → TDE on card columns
• Restrict access by business need → Least privilege, VPD
• Track and monitor access → Comprehensive auditing
• Regular testing → Vulnerability assessments
• Strong access control measures → MFA, password policies

SOX (Sarbanes-Oxley):
• Separation of duties → Database Vault
• Audit trails → Who changed financial records
• Change management → Controlled releases
• Data integrity → Constraints, triggers, validation
5 Virtual Private Database (VPD) hoạt động như thế nào? Use cases và limitations?
👁️ Xem Đáp Án
VPD Working Mechanism:
1. Create PL/SQL function trả về predicate (WHERE clause)
2. Register function với table/view qua DBMS_RLS
3. Every SQL statement, Oracle tự động append predicate
4. Predicate evaluated BEFORE query execution
5. User CANNOT see or bypass the predicate

Use Cases:
• Multi-tenant SaaS: customer_id = session context
• Department isolation: employee sees only their dept
• Geographic restrictions: regional data access
• Role-based data access: managers see more than staff
• Compliance: restrict PII access by authorization

VPD Policy Types:
• STATIC: Function result cached per statement
• CONTEXT_SENSITIVE: Re-evaluated when context changes
• SHARED_CONTEXT_SENSITIVE: Cached, best performance
• DYNAMIC: Evaluated every time (slowest)

Limitations:
• Function must be deterministic và fast
• Complex predicates can impact performance
• Debugging difficult (WHERE clause hidden)
• Direct path operations (SQL*Loader) bypass VPD
• Export/Import requires special handling

Best Practices:
• Use SHARED_CONTEXT_SENSITIVE for performance
• Keep predicates simple
• Use application context for user attributes
• Test performance với representative data volumes
• Document policies thoroughly

2. Password Policy Best Practices

Enterprise Password Policy Requirements:
  • Minimum 12 characters (14+ cho privileged accounts)
  • Complexity: Upper, lower, digits, special characters
  • History: Prevent reuse của 10 previous passwords
  • Expiration: 60-90 days (90 day standard)
  • Lockout: 3-5 failed attempts, 1 hour lock time
  • Grace period: 5-7 days warning before expiration

3. Oracle Wallet Architecture

Oracle Wallet provides secure external password store:

  • Auto-login wallet: No password needed, OS authenticated
  • File location: Protected by OS file permissions
  • Multiple credentials: One wallet, many database connections
  • TNS_ADMIN: Configure wallet location in sqlnet.ora

Ví Dụ 1: Custom Password Verify Function

-- Enterprise-grade password verify function
CREATE OR REPLACE FUNCTION enterprise_pwd_verify(
  username   VARCHAR2,
  password   VARCHAR2,
  old_password VARCHAR2
) RETURN BOOLEAN
IS
  n BOOLEAN;
  m INTEGER;
BEGIN
  -- Check 14 character minimum
  IF LENGTH(password) < 14 THEN
    raise_application_error(-20001, 
      'Password must be at least 14 characters');
  END IF;

  -- Check not same as username
  IF UPPER(password) = UPPER(username) THEN
    raise_application_error(-20002, 
      'Password cannot be same as username');
  END IF;

  -- Check complexity: upper, lower, digit, special
  IF NOT REGEXP_LIKE(password, '^.*[A-Z].*$') THEN
    raise_application_error(-20003, 
      'Password must contain uppercase');
  END IF;
  
  IF NOT REGEXP_LIKE(password, '^.*[a-z].*$') THEN
    raise_application_error(-20004, 
      'Password must contain lowercase');
  END IF;
  
  IF NOT REGEXP_LIKE(password, '^.*[0-9].*$') THEN
    raise_application_error(-20005, 
      'Password must contain digit');
  END IF;
  
  IF NOT REGEXP_LIKE(password, '^.*[!@#$%^&*()].*$') THEN
    raise_application_error(-20006, 
      'Password must contain special character');
  END IF;

  -- Check not common password
  IF password IN ('Welcome123!', 'Password123!',
      'Oracle123!', 'Admin123!') THEN
    raise_application_error(-20007, 
      'Password is too common');
  END IF;

  RETURN TRUE;
END;
/

Ví Dụ 3: Database Links Bảo Mật

-- Current User Link (Most Secure)
CREATE DATABASE LINK remote_secure
  CONNECT TO CURRENT_USER
  USING 'REMOTE_TNS';

-- Encrypt link communications
-- In sqlnet.ora on both sides:
SQLNET.ENCRYPTION_SERVER = REQUIRED
SQLNET.ENCRYPTION_TYPES_SERVER = (AES256)
SQLNET.CRYPTO_CHECKSUM_SERVER = REQUIRED
SQLNET.CRYPTO_CHECKSUM_TYPES_SERVER = (SHA256)

-- Restrict with view
CREATE OR REPLACE VIEW remote_emp_limited AS
SELECT employee_id, first_name, last_name, email
FROM employees@remote_secure
WHERE department_id = 50;

GRANT SELECT ON remote_emp_limited TO app_user;

-- Enable audit
AUDIT SELECT ON remote_emp_limited BY ACCESS;

1 Tại sao Oracle Wallet an toàn hơn hard-coded passwords?

Oracle Wallet an toàn hơn vì:
• Passwords encrypted trong wallet file
• OS file permissions protect wallet
• Không visible trong scripts hoặc process list
