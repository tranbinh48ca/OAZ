❓ 4. Câu Hỏi Ôn Tập
1Performance Tuning Oracle được tổ chức thành mấy phần? Liệt kê tên và mục tiêu?
🔍 Đáp án
3 phần: (1) Monitoring & Diagnostics — Dùng AWR/ADDM/ASH/V$ views để thu thập data, phát hiện và xác định vấn đề. (2) SQL Tuning — Xác định SQL chậm, tác động Optimizer, dùng SPA/SPM kiểm soát plan. (3) Instance Tuning — Sizing memory components (Shared Pool, Buffer Cache, PGA) và I/O subsystem.
2Tại sao "Tăng Buffer Cache Hit Ratio lên 99%" không phải mục tiêu tuning tốt?
🔍 Đáp án
Đây là technical metric, không phải business goal. Oracle khuyến nghị dùng DB Time reduction làm metric chính. Ngoài ra: Hit Ratio cao vẫn không cải thiện nếu bottleneck ở chỗ khác (CPU bound SQL, lock waits). Mục tiêu đúng: "Giảm response time trang X từ 8s xuống 2s", "Giảm batch ETL từ 4h xuống 2h".
3DB Time là gì? Tại sao nó là metric quan trọng nhất?
🔍 Đáp án
DB Time = Tổng thời gian CPU + thời gian wait (non-idle) của TẤT CẢ foreground sessions. Quan trọng vì: (1) Phản ánh tổng "công việc" database đang làm, (2) Có thể phân tích breakdown (SQL execute, parse, PL/SQL...), (3) Là nền tảng của AWR reports và ADDM, (4) Giảm DB Time = cải thiện performance thực sự.
45 bước General Tuning Session là gì? Tại sao "Measure Improvement" quan trọng?
🔍 Đáp án
5 bước: Collect Current State → Identify Top Problem → Investigate Root Cause → Implement Solution → Measure Improvement. "Measure" quan trọng vì: (1) Verify mục tiêu đã đạt chưa, (2) Phát hiện side effects, (3) Document evidence, (4) Tránh thay đổi nhiều biến cùng lúc — không đo lường thì không biết cái gì thực sự hiệu quả.
5FAST_START_MTTR_TARGET = 60 nghĩa là gì? Có ảnh hưởng gì đến performance?
🔍 Đáp án
Oracle đảm bảo instance recovery hoàn thành trong 60 giây sau crash. Oracle sẽ checkpoint thường xuyên hơn để đảm bảo không có quá nhiều dirty buffers. Trade-off: Checkpoint thường xuyên → tăng I/O write overhead → giảm throughput một chút. Cần cân bằng: business requirement về downtime tolerance vs throughput impact.

❓ 4. Câu Hỏi Ôn Tập
1V$ views có mất data khi restart instance không? Tại sao?
🔍 Đáp án
Có. V$ views là in-memory statistics — khi instance shutdown, tất cả data trong V$ views bị mất. Đây là lý do AWR quan trọng: MMON flush statistics từ memory ra disk (SYSAUX tablespace) định kỳ, tạo persistent history. DBA_HIST_* views lưu trữ historical data từ AWR snapshots.
2Sự khác nhau giữa "log file sync" (Commit class) và "log file parallel write" (System I/O)?
🔍 Đáp án
log file sync: User foreground session chờ khi COMMIT, phải đợi LGWR hoàn thành ghi redo buffer ra redo log file. Nếu cao → LGWR chậm → kiểm tra I/O speed redo log disks, tăng redo log size. log file parallel write: LGWR background process wait khi ghi redo. Thuộc System I/O class. Cả 2 liên quan đến redo log performance.
3SQL Trace level 12 bao gồm gì? Khi nào nên dùng?
🔍 Đáp án
Level 12 = Level 4 (SQL text + bind variable values) + Level 8 (wait events). Khi dùng: troubleshoot một SQL cụ thể đang chạy chậm, cần biết giá trị bind variables thực tế, và muốn thấy từng wait event trong quá trình execute. Sau đó dùng TKPROF format trace file để đọc dễ hơn.
4STATISTICS_LEVEL = BASIC gây ra vấn đề gì?
🔍 Đáp án
BASIC tắt timed statistics → AWR, ADDM, ASH không hoạt động hiệu quả. Không có time model data, không có wait time data. Về cơ bản vô hiệu hóa phần lớn Oracle's self-management và diagnostics infrastructure. Không bao giờ set BASIC trên production. Default TYPICAL có <5% overhead — hoàn toàn chấp nhận được.

FETCH FIRST 10 ROWS ONLY;

-- 3. Active sessions với blocking info

AND    t.sid = s.sid

📖 3. Giải Thích & Ví Dụ
AWR Architecture: MMON background process tự động flush in-memory statistics sang SYSAUX tablespace mỗi 60 phút (default). Snapshot = tập hợp statistics tại 1 thời điểm, unique SNAP_ID. AWR = Automatic Workload Repository — yêu cầu Oracle Diagnostics Pack license.

📊 Ví dụ 1: Quản lý AWR Settings

SQL
-- Xem AWR settings hiện tại
SELECT snap_interval, retention, topnsql
FROM   DBA_HIST_WR_CONTROL;

-- Thay đổi: interval 30 phút, retention 30 ngày
EXECUTE DBMS_WORKLOAD_REPOSITORY.MODIFY_SNAPSHOT_SETTINGS(
  interval  => 30,       -- phút (0 = tắt auto snapshot)
  retention => 43200     -- phút (43200 = 30 ngày)
);

-- Xem snapshots gần nhất
SELECT snap_id, begin_interval_time, end_interval_time
FROM   DBA_HIST_SNAPSHOT
WHERE  begin_interval_time > SYSDATE - 2
ORDER BY snap_id DESC
FETCH FIRST 10 ROWS ONLY;

🔍 Đáp án

🔍 Đáp án

🔍 Đáp án
MMON (Manageability Monitor): Background process thực hiện: (1) Flush in-memory statistics sang SYSAUX mỗi interval (tạo snapshot), (2) Trigger ADDM analysis sau mỗi snapshot, (3) Compute metrics từ base statistics, (4) Manage AWR space (purge old snapshots), (5) Handle server-generated alerts khi threshold vi phạm.

❓ 4. Câu Hỏi Ôn Tập
1Tại sao Metrics tốt hơn raw Statistics cho proactive monitoring?
🔍 Đáp án
Raw statistics = cumulative counters từ khi startup (ví dụ: 1 triệu logical reads). Tự chúng không có ý nghĩa để compare. Metrics = rate per time (logical reads/sec) → có thể set threshold, compare giờ này vs giờ khác, trending over time. Metrics cũng đã tính sẵn, không cần capture trước/sau thủ công.
2Server-Generated Alert là gì? Kể 3 loại phổ biến.
🔍 Đáp án
Oracle tự monitor metrics và tạo alert khi threshold vi phạm. 3 loại phổ biến: (1) Tablespace % Full — Warning 85%, Critical 97% (built-in default), (2) CPU Utilization Limit — set theo nhu cầu, (3) Average Active Sessions — khi số active sessions vượt số CPUs. Alerts gửi đến DBA_OUTSTANDING_ALERTS và EM notifications.
3V$SYSMETRIC với group_id=1 vs group_id=2 khác nhau thế nào?
🔍 Đáp án
group_id=2 (Long Duration): 60-second interval metrics — interval 60 giây, keep history 1 giờ. group_id=1 (Short Duration): 15-second interval metrics — interval 15 giây, chỉ keep 1 interval (current value). Short duration dùng cho real-time fine-grained monitoring. Long duration dùng cho trending và alert thresholds.

❓ 4. Câu Hỏi Ôn Tập
1Hard Parse vs Soft Parse — Sự khác biệt và cách giảm Hard Parse?
🔍 Đáp án
Hard Parse: SQL không tìm thấy trong shared pool → phải syntax check, semantic check, privilege check, generate execution plan → tốn CPU, shared pool latch. Soft Parse: Tìm thấy match trong shared pool → chỉ cần syntax/security check → rẻ hơn nhiều. Giảm Hard Parse: (1) Dùng Bind Variables thay vì literals, (2) Tăng SESSION_CACHED_CURSORS, (3) Tăng SHARED_POOL_SIZE, (4) Set CURSOR_SHARING=FORCE nếu không thể đổi code.
2DBMS_XPLAN.DISPLAY_CURSOR với format 'ALLSTATS LAST' cho biết gì đặc biệt?
🔍 Đáp án
'ALLSTATS LAST' hiển thị ACTUAL row counts và ACTUAL buffer gets (thực tế khi thực thi) bên cạnh ESTIMATED row counts từ optimizer. Nếu estimated rows khác xa actual rows → statistics không chính xác → optimizer đang chọn sub-optimal plan. Yêu cầu STATISTICS_LEVEL=ALL hoặc hint /*+ GATHER_PLAN_STATISTICS */.
3TKPROF sort option "exeela" là gì? Cho ví dụ các sort options khác.
🔍 Đáp án
exeela = Sort by elapsed time during Execute phase. Khác: prsela (parse elapsed), fchela (fetch elapsed), execpu (execute CPU time), prscnt (parse count — tìm SQL bị parse nhiều), exerow (rows processed during execute). Thường dùng: sort=exeela để thấy SQL tốn thời gian nhất khi chạy; sort=prscnt để thấy SQL bị hard parse nhiều nhất.
4Khi TKPROF hiển thị DISK (physical reads) cao cho một SQL, có thể làm gì?
🔍 Đáp án
Nguyên nhân và solutions: (1) Data không có trong buffer cache → tăng DB_CACHE_SIZE, (2) Index range scan trả về quá nhiều rows → xem xét lại index, (3) Full Table Scan trên bảng lớn → thêm selective index, (4) First execution (cold cache) → đây là normal, không phải vấn đề, (5) Partition pruning không hoạt động → kiểm tra partition key trong WHERE clause.
5Làm thế nào để tìm execution plan cũ của SQL đã từng chạy nhưng bị age out khỏi shared pool?
🔍 Đáp án
Dùng DBA_HIST_SQL_PLAN (AWR) nếu SQL đã được capture vào AWR snapshot: SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_AWR('sql_id'));. Nếu SQL không có trong AWR (không phải top SQL), và bị age out → không thể recover plan đó. Preventive: tạo SQL Plan Baseline để capture và preserve important SQL plans.

❓ 4. Câu Hỏi Ôn Tập
1CBO hoạt động như thế nào? 3 bước chính?
🔍 Đáp án
(1) Query Transformer: Rewrite query nếu beneficial (view merging, subquery unnesting, predicate pushing). (2) Estimator: Tính Selectivity (fraction of rows) → Cardinality (# rows) → Cost (I/O + CPU, normalized to block reads). Dùng statistics và histograms. (3) Plan Generator: Test nhiều combinations (access paths, join methods, join orders) → chọn plan có lowest cost.
2Histograms là gì và khi nào cần tạo?
🔍 Đáp án
Histogram = Phân phối tần suất của values trong column. Cần khi: column có skewed data distribution (một vài values chiếm phần lớn rows). Ví dụ: STATUS column, 95% = 'ACTIVE', 5% = 'INACTIVE' → WITHOUT histogram, optimizer giả định 50/50 → wrong cardinality → bad plan. WITH histogram → optimizer biết 'INACTIVE' = 5% → chọn đúng access path.
3Hints nên dùng khi nào? Rủi ro gì?
🔍 Đáp án
Hints là last resort. Dùng khi: biết chắc một plan tốt hơn nhưng optimizer không chọn nó, statistics đúng nhưng optimizer vẫn sai. Rủi ro: (1) Hints cứng nhắc — không adapt khi data thay đổi, (2) Developer có thể không biết hint trong code → khó maintain, (3) Một plan tốt hôm nay có thể không tốt sau 6 tháng data thay đổi. Ưu tiên: Fix statistics → Extended stats → SQL Profile → Hints.
📝 5. Tổng Kết

🌟 Module 10 — Key Points

  • CBO = Query Transformer → Estimator → Plan Generator
  • Selectivity: fraction of rows; Cardinality: # rows; Cost: normalized I/O+CPU
  • Quality statistics = CBO makes good decisions → gather stats regularly
  • Histograms: critical cho skewed data distribution
  • Optimizer mode: ALL_ROWS (default) vs FIRST_ROWS_n (OLTP)
  • Hints: last resort, prefer statistics fix and SQL Profile

1INDEX REBUILD vs COALESCE — Khi nào dùng cái nào?

❓ 4. Câu Hỏi Ôn Tập
1RELOADS trong V$LIBRARYCACHE nghĩa là gì? Cao thì làm gì?
🔍 Đáp án
RELOADS = Số lần SQL statement bị parse lại vì đã bị aged out khỏi Library Cache (không đủ memory). Cao RELOADS → Shared Pool quá nhỏ → SQL bị kick ra trước khi được reuse. Solutions: (1) Tăng SHARED_POOL_SIZE, (2) Dùng DBMS_SHARED_POOL.KEEP cho critical packages, (3) Dùng Bind Variables để reduce number of unique SQL statements, (4) Dùng V$SHARED_POOL_ADVICE để size appropriately.
2Latch và Mutex khác nhau thế nào trong Oracle 11g?
🔍 Đáp án
Latch: 1 latch protect nhiều objects → khi hot object gây contention, toàn bộ objects trong chain bị ảnh hưởng (false contention). Mutex: 1 mutex per cursor/object → finer granularity, ít false contention hơn. Trong 11g, Library Cache dùng mutexes thay latches → scalable hơn nhiều. Mutex cũng là pin mechanism (ref count thay cho library cache pin).
3CURSOR_SHARING = FORCE có risk gì?
🔍 Đáp án
Risks: (1) Bind variable peeking: Oracle peek giá trị bind lần đầu → chọn plan dựa trên value đó. Nếu lần sau giá trị khác (ví dụ: skewed data), plan cũ có thể sub-optimal. (2) Không phải mọi literal đều có thể replace safely (ví dụ: string literals trong DDL). (3) Overhead khi parsing để identify literals. Best practice: Fix application code để dùng bind variables properly.
📝 5. Tổng Kết

🌟 Module 15 — Key Points

  • Shared Pool = Library Cache + Dictionary Cache + Results Cache + UGA
  • Library Cache key metrics: RELOADS (aging out) và INVALIDATIONS (DDL/stats)
  • V$SHARED_POOL_ADVICE: size recommendations với time_saved_factor
  • Bind Variables: cách tốt nhất giảm Hard Parse
  • CURSOR_SHARING=FORCE: fix app không dùng bind vars (với trade-offs)
  • DBMS_SHARED_POOL.KEEP: pin critical packages khỏi aging out

Tuning the Buffer Cache

★ Instance TuningBuffer CachePhysical Reads
📖 3. Giải Thích & Ví Dụ
Buffer Cache = Set of memory buffers in SGA — mỗi buffer = 1 database block. Goal: giữ "hot" data trong memory, tránh physical I/O. LRU algorithm quyết định buffer nào bị evict.

📊 Ví dụ 1: Buffer States và Working Sets

3 trạng thái buffer: FREE (empty/same as disk — available to overwrite) | DIRTY (modified, not yet written to disk) | PINNED (being accessed — max 1 writer, many readers). Working Sets = subsets of buffers với 1 LRU list + 2 checkpoint queues → improve scalability trên multi-CPU.

       NULLIF(db_block_gets + consistent_gets, 0), 2) cache_hit_ratio
FROM (
  SELECT
    SUM(CASE WHEN name = 'db block gets from cache'    THEN value END) db_block_gets,
    SUM(CASE WHEN name = 'consistent gets from cache'  THEN value END) consistent_gets,
    SUM(CASE WHEN name = 'physical reads cache'       THEN value END) physical_reads
  FROM   V$SYSSTAT
);

❓ 4. Câu Hỏi Ôn Tập
1Buffer Busy Waits vs Free Buffer Waits — Phân biệt và giải pháp?
🔍 Đáp án
Buffer Busy Waits: Session đang chờ buffer đang bị PIN bởi session khác. Nguyên nhân: hot block (segment header block, index root/branch blocks). Solutions: use Automatic Segment Space Management, reverse key indexes cho sequences. Free Buffer Waits: Không có free buffer để load block mới → DBWn chưa ghi dirty buffers kịp. Solutions: tăng DB_CACHE_SIZE, tăng DB_WRITER_PROCESSES, check I/O throughput.
2Khi nào nên dùng KEEP pool? RECYCLE pool?
🔍 Đáp án
KEEP pool: Tables/indexes luôn cần trong cache — lookup tables, reference data, frequently accessed medium-size tables. Tránh bị evicted bởi LRU. RECYCLE pool: Very large tables accessed infrequently (scanned but not repeatedly). Tránh chúng pollute default buffer cache và evict "hot" blocks. DEFAULT pool: Hầu hết tables — automatic LRU management.
3Consistent Read (CR) Clone là gì? Ảnh hưởng gì đến buffer cache?
🔍 Đáp án
CR Clone = Copy của block được tạo để đảm bảo read consistency. Khi SELECT cần thấy block với undo data applied (consistent với thời điểm query start) → Oracle copy block sang buffer mới, apply undo → tạo CR clone. Nhiều CR clones → chiếm buffer cache space. Long-running queries + heavy DML = nhiều CR clones cần = tăng cache pressure.
📝 5. Tổng Kết

🌟 Module 16 — Key Points

  • Buffer states: FREE, DIRTY, PINNED — LRU manages replacement
  • V$DB_CACHE_ADVICE: predict physical reads vs cache size — use it!
  • KEEP pool: pin hot small tables; RECYCLE: isolate large scan tables
  • free buffer waits → tăng cache size hoặc thêm DBWn processes
  • buffer busy waits → hot blocks → ASSM, reverse key index
  • FAST_START_MTTR_TARGET: balance recovery time vs checkpoint I/O

1Optimal mode vs Multi-pass mode — Tại sao Multi-pass cực kỳ nguy hiểm?

1AMM vs ASMM — Khi nào dùng cái nào?
🔍 Đáp án

2Granule là gì? Kích thước granule phụ thuộc vào gì?

Xem qua V$SGAINFO WHERE name='Granule Size'.

-- DB_WRITER_PROCESSES: số DBWn background processes
-- Mặc định = 1, tăng khi write bottleneck
ALTER SYSTEM SET db_writer_processes = 4 SCOPE=SPFILE;
-- Cần restart, thường = 1/8 CPU count (max 20)
📤 I/O Analysis
-- Interpretations: avg_read_ms > 20ms → I/O latency problem (should be < 10ms for SSD, < 20ms HDD) avg_write_ms > 20ms → write I/O problem → check LGWR, DBWn phyrds/phywrts very high on 1 file → hot file → need striping/ASM rebalance free buffer waits + avg_read_ms high → buffer cache + I/O both need tuning
❓ 4. Câu Hỏi Ôn Tập
1Direct I/O giải quyết vấn đề gì? Tại sao Oracle khuyến nghị?
🔍 Đáp án
Vấn đề: Standard I/O qua OS buffer cache = data được copy 2 lần (OS cache → Oracle buffer). Oracle đã có buffer cache của mình → OS cache là redundant. Direct I/O: bypass OS cache → data đi thẳng từ disk vào Oracle buffer cache → (1) Giải phóng OS memory cho SGA, (2) Tránh double-copy, (3) Larger I/O transfers possible, (4) Reduce CPU overhead. Oracle strongly recommends Direct I/O trên bất kỳ OS file system nào support it.
2OLTP và DW/OLAP cần loại I/O metric khác nhau thế nào?
🔍 Đáp án
OLTP: Small random I/O (8KB-16KB blocks), many small transactions, cần IOPS (I/O Operations Per Second) cao → High RPM disks, nhiều disks, SSD. Latency per I/O quan trọng. DW/OLAP: Large sequential I/O (multi-block reads), cần MB/s bandwidth cao → Large I/O channels, RAID striping rộng, nhiều disks. Throughput per operation quan trọng hơn latency.
3Tại sao tăng số disks quan trọng hơn tăng disk size cho Oracle performance?
🔍 Đáp án
I/O bandwidth = (Số disks × bandwidth/disk). Một disk 2TB không nhanh hơn một disk 1TB cùng RPM. Nhiều disks = parallel I/O = tổng IOPS và MB/s tăng. Ví dụ: 4 disks × 160MB/s = 640MB/s. RAID striping phân tán I/O đồng đều → tất cả disks được dùng. Disk controllers cũng là bottleneck: 1 SCSI controller 600MB/s chỉ handle ~4 fast disks efficiently.
📝 5. Tổng Kết

🌟 Module 19 — Key Points

  • I/O modes: Standard(unsafe) → Synchronous → Async → Direct I/O (best)
  • FILESYSTEMIO_OPTIONS=SETALL: Direct + Async — khuyến nghị production
  • ASM = Auto Storage Mgmt: Direct I/O + Striping + Mirroring + Rebalancing
  • OLTP: IOPS metric — high RPM, fast seek; DW: MB/s — large channels
  • I/O bandwidth = # disks × bandwidth/disk (không phải capacity!)
  • DB_WRITER_PROCESSES: tăng khi free buffer waits cao (write bottleneck)

❓ 4. Câu Hỏi Ôn Tập
1Redo log files nên to cỡ bao nhiêu? Rule of thumb là gì?
🔍 Đáp án
Redo log files nên trong range 100MB → vài GB. Rule of thumb: Switch log files tối đa 1 lần / 20 phút trong peak workload. Nếu switch nhanh hơn → redo log quá nhỏ → tăng size hoặc thêm groups. Oracle cũng cung cấp V$INSTANCE_RECOVERY.OPTIMAL_LOGFILE_SIZE để tính toán dựa trên FAST_START_MTTR_TARGET.
2Tại sao STATISTICS_LEVEL = BASIC rất nguy hiểm trên production?
🔍 Đáp án
BASIC tắt hầu hết timed statistics → (1) AWR snapshots không capture useful data, (2) ADDM không hoạt động (không có time model data), (3) ASH không hoạt động, (4) Automatic Shared Memory Management không tối ưu được, (5) SQL Monitoring không available. Basically vô hiệu Oracle's entire self-management và diagnostics infrastructure. Overhead của TYPICAL là <5% — hoàn toàn chấp nhận được.
3OPEN_CURSORS = 500 nghĩa là gì? Quá thấp có hậu quả gì?
🔍 Đáp án
OPEN_CURSORS = max number of cursors mỗi session có thể có open cùng lúc. Quá thấp → ORA-01000: maximum open cursors exceeded. Dấu hiệu: V$SESSTAT thống kê "opened cursors current" gần với OPEN_CURSORS. Tăng lên 500-1000 là safe. Cũng check: application đang mở cursors nhưng không đóng (cursor leak) → fix app code thay vì chỉ tăng limit mãi.
4LOG_ARCHIVE_MAX_PROCESSES mặc định là bao nhiêu? Khi nào cần tăng?
🔍 Đáp án
Default = 2 ARCn processes. Tăng khi: (1) V$ARCHIVE_DEST_STATUS shows "not archiving" hoặc lag growing, (2) Nhiều redo log groups đang wait to be archived, (3) Peak workload tạo redo nhanh hơn ARCn có thể archive. Tăng lên 4-6 cho busy production. LGWR tự start thêm ARCn khi cần, không vượt LOG_ARCHIVE_MAX_PROCESSES.
5Performance Tuning là một lần hay liên tục? Tại sao?
🔍 Đáp án
Liên tục. Vì: (1) Data volume tăng → statistics stale → optimizer plans thay đổi, (2) Application thay đổi → new SQL patterns, (3) Seasonal spikes (Black Friday, month-end), (4) Hardware/OS upgrades, (5) Oracle version upgrades (CBO improvements → different plans). DBA cần: daily monitoring (AWR, ADDM alerts), weekly performance reviews, và proactive capacity planning dựa trên trends.
