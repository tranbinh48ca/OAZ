# PHẦN 1: TỔNG QUAN HỆ SINH THÁI DATABASE

## 1.1 ACID vs BASE

| Tiêu chí | ACID (RDBMS) | BASE (đa số NoSQL) |
|---|---|---|
| Atomicity | Transaction toàn-hoặc-không | Basically Available — ưu tiên luôn phản hồi |
| Consistency | Dữ liệu luôn nhất quán ngay | Soft state — trạng thái có thể thay đổi |
| Isolation | Transaction song song không ảnh hưởng nhau | — |
| Durability | Commit rồi không mất | Eventual consistency — cuối cùng nhất quán |
| Phù hợp | Tiền, cước, hợp đồng, giao dịch tài chính | Session, cache, log, activity feed |

## 1.2 CAP Theorem áp dụng thực tế

| Hệ thống | Ưu tiên | Ý nghĩa thực tế |
|---|---|---|
| Oracle RAC, PostgreSQL (Sync) | **CP** | Thà từ chối phục vụ còn hơn trả dữ liệu sai — đúng cho core banking |
| MongoDB (default), Cassandra | **AP** | Luôn phản hồi, chấp nhận dữ liệu chưa đồng bộ ngay — đúng cho session/CDR |
| Redis Sentinel | **CP** thiên hướng | Failover có kiểm soát |

## 1.3 Bảng tổng quan 6 nhóm công nghệ

| Nhóm | Đại diện | Mô hình dữ liệu | Đặc tính nổi bật |
|---|---|---|---|
| RDBMS | Oracle, PostgreSQL, SQL Server, MySQL | Bảng quan hệ, schema cố định | ACID mạnh, JOIN phức tạp |
| NoSQL Document | MongoDB, Couchbase | JSON/BSON linh hoạt | Schema-less, scale ngang dễ |
| NoSQL Key-Value | Redis, DynamoDB | Key → Value | Tốc độ cực cao (sub-ms) |
| NoSQL Wide-Column | Cassandra, HBase | Bảng cực rộng, phân tán | Ghi khối lượng cực lớn |
| Graph | Neo4j, Amazon Neptune | Node + Edge | Truy vấn quan hệ nhiều bước cực nhanh |
| Big Data/Hadoop | HDFS, Hive, Spark | File phân tán + Schema-on-read | Lưu trữ PB, xử lý batch |

# PHẦN 2: KHI NÀO DÙNG LOẠI DATABASE NÀO

## Nhóm A: RDBMS — khi cần ACID tuyệt đối

**Dùng khi:** dữ liệu liên quan trực tiếp TIỀN (billing, thanh toán, số dư); nhiều ràng buộc toàn vẹn tham chiếu phức tạp; cần transaction đa bảng rollback tuyệt đối; cần JOIN phức tạp cho báo cáo chính xác.

| Tiêu chí | Oracle | PostgreSQL | SQL Server | MySQL |
|---|---|---|---|---|
| Mission-critical, HA cao nhất | ✅✅✅ | ✅✅ (Patroni) | ✅✅ (AlwaysOn) | ✅ |
| Chi phí license | Cao | Miễn phí | Trung bình-cao | Miễn phí |
| Hệ sinh thái enterprise | ✅✅✅ (PL/SQL, GoldenGate) | Tương đương qua extension | ✅✅ (T-SQL) | Hạn chế |
| Phù hợp | Core banking, billing lớn (>10TB), SLA 99.999% | Ứng dụng mới, tối ưu chi phí, JSON native | Môi trường .NET/Windows | Web app vừa/nhỏ |

**Ví dụ quyết định:** Billing/Charging real-time nhà mạng lớn → **Oracle** (RAC+Data Guard) vì cần chục nghìn TPS zero data loss. CRM nội bộ quy mô vừa → **PostgreSQL** để tối ưu chi phí.

## Nhóm B: NoSQL Document/Key-Value — khi schema linh hoạt

**MongoDB khi:** cấu trúc thay đổi thường xuyên theo sản phẩm/gói cước; dữ liệu tự nhiên dạng document lồng nhau; cần scale ngang dễ; không cần JOIN phức tạp.

**Redis khi:** cần tốc độ dưới mili-giây (session, OTP, rate limiting); dữ liệu tạm thời có TTL; cấu trúc đơn giản.

**Ví dụ:** Session app di động, cache tra cứu gói cước → **Redis**. Hồ sơ Customer 360 tổng hợp nhiều nguồn → **MongoDB**.

## Nhóm C: Wide-Column/Time-Series — khi ghi khối lượng cực lớn

**Cassandra/HBase khi:** khối lượng ghi cực lớn (CDR hàng tỷ bản ghi/ngày); cần scale ngang tuyến tính, masterless; truy vấn theo partition key đã biết.

**Time-Series (InfluxDB/TimescaleDB) khi:** dữ liệu bản chất theo dòng thời gian (KPI mạng, IoT/5G); cần hàm tổng hợp theo cửa sổ thời gian.

**Ví dụ:** CDR 500 triệu bản ghi/ngày → **Cassandra**. KPI trạm 5G mỗi giây → **TimescaleDB**.

## Nhóm D: Graph Database — khi trọng tâm là quan hệ

**Neo4j khi:** bài toán cốt lõi là tìm quan hệ nhiều bước (traversal); phát hiện gian lận (fraud ring); phân tích mạng lưới thuê bao; AML sở hữu doanh nghiệp phức tạp.

**Ví dụ:** Fraud SIM box, AML rửa tiền → **Neo4j** vì RDBMS self-join 5-6 cấp chậm theo cấp số nhân, Graph traversal gần tuyến tính.

## Nhóm E: Big Data/Hadoop — khi lưu trữ/phân tích PB dữ liệu

**HDFS/Hive/Spark khi:** cần lưu RAW DATA khối lượng PB đa dạng định dạng; xử lý batch dài hạn (churn prediction, training ML); chi phí lưu trữ commodity hardware rẻ; chấp nhận độ trễ phút/giờ.

**Ví dụ:** Data Lake CDR/log network 5 năm cho phân tích churn → **Hadoop**, kết quả tổng hợp mới đẩy vào RDBMS/DWH cho BI.

# PHẦN 3: ÁNH XẠ LOẠI ỨNG DỤNG ↔ DATABASE PHÙ HỢP

## 3.1 Ngành Viễn thông

| Loại ứng dụng | Database khuyến nghị | Lý do |
|---|---|---|
| Billing/Charging real-time | **Oracle** (hoặc PostgreSQL quy mô vừa) | ACID, transaction tài chính, throughput cao |
| CDR lưu trữ thô | **Cassandra** hoặc **HDFS** | Ghi cực lớn, ít update, scale ngang |
| Customer 360/CRM hợp nhất | **MongoDB** | Bán cấu trúc, schema thay đổi theo sản phẩm |
| Session App/Portal | **Redis** | Tốc độ, TTL tự động |
| Network Topology/Inventory | **Neo4j** hoặc PostgreSQL+PostGIS | Quan hệ node-link, dữ liệu địa lý BTS |
| Fraud Detection (SIM box) | **Neo4j** + Kafka streaming | Phát hiện pattern quan hệ real-time |
| KPI mạng 5G/IoT | **TimescaleDB/InfluxDB** | Time-series tối ưu |
| Data Lake/phân tích dài hạn | **Hadoop (Hive/Spark)** | Lưu PB, batch processing |
| Recommendation gói cước | **MongoDB** + Redis cache | Linh hoạt, tốc độ real-time |
| Data Warehouse/BI | **Oracle Exadata** hoặc PostgreSQL+ClickHouse | Truy vấn phân tích phức tạp |

# PHẦN 4: KIẾN TRÚC THAM CHIẾU POLYGLOT PERSISTENCE

Doanh nghiệp lớn không dùng "một database cho tất cả" — kiến trúc thực tế là **polyglot persistence**:

```
                        ┌─────────────────────────────┐
                        │   API Gateway (Kong/Apigee)   │
                        └───┬─────────────┬────────────┘
         ┌──────────────────┘             └──────────────────┐
         ▼                                                     ▼
┌──────────────────┐                                  ┌──────────────────┐
│  Billing Service    │                                  │  Customer Service  │
│  (ACID) → Oracle RAC │                                  │  → MongoDB           │
└─────────┬──────────┘                                  └─────────┬──────────┘
          ▼                                                          ▼
┌──────────────────┐          ┌──────────────────┐        ┌──────────────────┐
│  Session/Cache      │          │  CDR Ingestion     │        │  Fraud Detection    │
│  → Redis Cluster     │          │  → Kafka→Cassandra  │        │  → Neo4j             │
└──────────────────┘          └─────────┬──────────┘        └──────────────────┘
                                          ▼ (ETL/Spark batch)
                               ┌──────────────────────┐
                               │  Data Lake/DWH           │
                               │  HDFS+Hive → Oracle DWH   │
                               │  → BI/Reporting            │
                               └──────────────────────┘

Nguyên tắc: mỗi service SỞ HỮU RIÊNG database (Database per Service), đồng bộ
qua event streaming (Kafka), KHÔNG chia sẻ trực tiếp database giữa các service.
```

# PHẦN 5: HƯỚNG DẪN MIGRATION CHI TIẾT

## Quy trình chuẩn 6 bước cho MỌI migration

```
1. ASSESSMENT    — Kiểm kê schema, object, khối lượng dữ liệu
2. SCHEMA CONVERT — Chuyển đổi cấu trúc bảng, kiểu dữ liệu, ràng buộc
3. CODE CONVERT   — Chuyển PL/SQL/T-SQL, connection string ứng dụng
4. DATA MIGRATION — Full load + CDC đồng bộ liên tục
5. VALIDATION     — Đối chiếu row count, checksum, dual-run test
6. CUTOVER        — Chuyển traffic thật, có kế hoạch ROLLBACK
```

## 5.1 Oracle → MySQL

**Khi nào:** web/portal quy mô vừa, không cần PL/SQL nặng/partitioning phức tạp, giảm chi phí license.

**Công cụ:** AWS SCT (Schema Conversion Tool) + AWS DMS, hoặc thủ công.

```sql
-- Bảng ánh xạ kiểu dữ liệu Oracle → MySQL
-- NUMBER(p,s)  → DECIMAL(p,s)         VARCHAR2(n) → VARCHAR(n)
-- CLOB         → LONGTEXT              BLOB        → LONGBLOB
-- DATE         → DATETIME              SEQUENCE    → AUTO_INCREMENT (khác biệt lớn nhất)
-- ROWNUM       → LIMIT                 NVL()       → IFNULL()
-- CONNECT BY   → WITH RECURSIVE (MySQL 8.0+)

-- Oracle SEQUENCE:
CREATE SEQUENCE seq_customer_id START WITH 1 INCREMENT BY 1;
INSERT INTO customers (id, name) VALUES (seq_customer_id.NEXTVAL, 'Nguyen Van A');

-- MySQL AUTO_INCREMENT tương đương:
CREATE TABLE customers (id INT AUTO_INCREMENT PRIMARY KEY, name VARCHAR(200));
INSERT INTO customers (name) VALUES ('Nguyen Van A');
```

```bash
# Export Oracle ra CSV
sqlplus user/pass@ORCLPDB1 << 'EOF'
SET COLSEP ',' PAGESIZE 0 TRIMSPOOL ON
SPOOL customers.csv
SELECT id||','||name||','||phone FROM customers;
SPOOL OFF
EOF

# Import vào MySQL
mysql -u root -p mydb << 'EOF'
LOAD DATA LOCAL INFILE 'customers.csv' INTO TABLE customers
FIELDS TERMINATED BY ',' LINES TERMINATED BY '\n' (id, name, phone);
EOF

# Khối lượng lớn + CDC liên tục: dùng AWS DMS
aws dms create-replication-task \
  --replication-task-identifier oracle-to-mysql-cdc \
  --source-endpoint-arn arn:aws:dms:...:endpoint:oracle-source \
  --target-endpoint-arn arn:aws:dms:...:endpoint:mysql-target \
  --migration-type full-load-and-cdc --table-mappings file://table-mappings.json
```

```sql
-- Chuyển PL/SQL Procedure sang MySQL Stored Procedure
-- Oracle:
CREATE OR REPLACE PROCEDURE update_balance(p_cust_id NUMBER, p_amount NUMBER) IS
BEGIN
  UPDATE accounts SET balance = balance + p_amount WHERE customer_id = p_cust_id;
  IF SQL%ROWCOUNT = 0 THEN RAISE_APPLICATION_ERROR(-20001, 'Customer not found'); END IF;
  COMMIT;
END;
/
-- MySQL:
DELIMITER $$
CREATE PROCEDURE update_balance(IN p_cust_id INT, IN p_amount DECIMAL(15,2))
BEGIN
  UPDATE accounts SET balance = balance + p_amount WHERE customer_id = p_cust_id;
  IF ROW_COUNT() = 0 THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Customer not found'; END IF;
END$$
DELIMITER ;
```

```sql
-- Ví dụ chuyển PL/SQL Package sang PL/pgSQL (package → schema + function riêng lẻ)
-- Oracle:
CREATE OR REPLACE PACKAGE BODY billing_pkg AS
  PROCEDURE charge_customer(p_id IN customers.id%TYPE, p_amount IN NUMBER) IS
    insufficient_balance EXCEPTION;
  BEGIN
    UPDATE accounts SET balance = balance - p_amount WHERE customer_id = p_id;
    IF (SELECT balance FROM accounts WHERE customer_id = p_id) < 0 THEN
      RAISE insufficient_balance;
    END IF;
    COMMIT;
  EXCEPTION
    WHEN insufficient_balance THEN
      ROLLBACK; RAISE_APPLICATION_ERROR(-20001, 'Số dư không đủ');
  END;
END billing_pkg;
/

-- PostgreSQL:
CREATE SCHEMA IF NOT EXISTS billing_pkg;
CREATE OR REPLACE FUNCTION billing_pkg.charge_customer(p_id customers.id%TYPE, p_amount NUMERIC)
RETURNS VOID AS $$
BEGIN
  UPDATE accounts SET balance = balance - p_amount WHERE customer_id = p_id;
  IF (SELECT balance FROM accounts WHERE customer_id = p_id) < 0 THEN
    RAISE EXCEPTION 'Số dư không đủ' USING ERRCODE = '20001';
  END IF;
END;
$$ LANGUAGE plpgsql;
```

## 5.3 Oracle → SQL Server (dùng SSMA)

**Khi nào:** hạ tầng .NET/Windows-centric, tích hợp Power BI/Azure/Active Directory.

**Quy trình SSMA (SQL Server Migration Assistant for Oracle — công cụ chính thức miễn phí):**
```
1. Cài SSMA for Oracle (Windows) → New Project, chọn SQL Server version đích
2. Connect to Oracle (TNS/connection string) + Connect to SQL Server đích
3. Oracle Metadata Explorer: chọn schema → kéo sang panel phải
4. "Convert Schema" → xem "Conversion Report" (% tự động, cảnh báo cần sửa tay)
5. "Synchronize with Database" → tạo schema thật trên SQL Server
```

```sql
-- Ánh xạ kiểu dữ liệu Oracle → SQL Server
-- NUMBER → DECIMAL/NUMERIC/INT     VARCHAR2(4000) → VARCHAR(4000)/NVARCHAR(MAX)
-- CLOB → VARCHAR(MAX)/NVARCHAR(MAX)  DATE → DATETIME2
-- SEQUENCE → IDENTITY hoặc SEQUENCE object (SQL Server 2012+)
-- PACKAGE → Schema + nhiều Stored Procedure riêng lẻ

-- Cursor Oracle → T-SQL
-- Oracle:
DECLARE
  CURSOR c_customers IS SELECT id, name FROM customers WHERE status = 'ACTIVE';
BEGIN
  FOR rec IN c_customers LOOP
    UPDATE accounts SET last_review = SYSDATE WHERE customer_id = rec.id;
  END LOOP;
  COMMIT;
END;
/
-- SQL Server:
DECLARE @id INT, @name NVARCHAR(200);
DECLARE c_customers CURSOR FOR SELECT id, name FROM customers WHERE status = 'ACTIVE';
OPEN c_customers;
FETCH NEXT FROM c_customers INTO @id, @name;
WHILE @@FETCH_STATUS = 0
BEGIN
    UPDATE accounts SET last_review = GETDATE() WHERE customer_id = @id;
    FETCH NEXT FROM c_customers INTO @id, @name;
END
CLOSE c_customers; DEALLOCATE c_customers;
```

```sql
  address_type VARCHAR2(20), full_address VARCHAR2(500));

SELECT c.name, a.full_address, s.plan_name FROM customers c
JOIN addresses a ON a.customer_id = c.id
```

```python
# migrate_oracle_to_mongo.py - KHÔNG có công cụ tự động "convert schema" vì bản chất
# migration này đòi hỏi redesign, không phải convert 1-1
import cx_Oracle
from pymongo import MongoClient
from datetime import datetime

oracle_conn = cx_Oracle.connect("user/password@oracle-host:1521/ORCLPDB1")
mongo_db = MongoClient("mongodb://mongo-host:27017/")["telco_customer360"]

cursor = oracle_conn.cursor()
cursor.execute("SELECT id, name, email FROM customers")
batch = []
for cust_id, name, email in cursor:
    addr_cursor = oracle_conn.cursor()
    addr_cursor.execute("SELECT address_type, full_address FROM addresses WHERE customer_id = :1", [cust_id])
    addresses = [{"type": t, "full_address": a} for t, a in addr_cursor]

    sub_cursor = oracle_conn.cursor()
    sub_cursor.execute("SELECT plan_name, start_date, status FROM subscriptions WHERE customer_id = :1", [cust_id])
    subscriptions = [{"plan_name": p, "start_date": d, "status": s} for p, d, s in sub_cursor]

    doc = {"customer_id": cust_id, "name": name, "email": email,
           "addresses": addresses, "subscriptions": subscriptions,
           "migrated_at": datetime.utcnow()}
    batch.append(doc)
    if len(batch) >= 1000:
        mongo_db.customers.insert_many(batch)
        batch = []
if batch:
    mongo_db.customers.insert_many(batch)
print("Migration hoàn tất!")
```

```sql
-- Ánh xạ kiểu dữ liệu PostgreSQL → Oracle
-- SERIAL/BIGSERIAL → NUMBER+SEQUENCE+TRIGGER (hoặc IDENTITY từ Oracle 12c+)
-- TEXT → CLOB (hoặc VARCHAR2(4000) nếu chắc chắn ngắn)
-- JSONB → JSON (Oracle 21c+ native) hoặc CLOB+CHECK constraint
-- BOOLEAN → NUMBER(1) hoặc CHAR(1) CHECK ('Y'/'N')
-- ARRAY → không hỗ trợ trực tiếp, cần bảng con hoặc VARRAY

-- PostgreSQL:
CREATE TABLE customers (id SERIAL PRIMARY KEY, name TEXT, metadata JSONB);

-- Oracle 12c+ tương đương:
CREATE TABLE customers (
  id NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name CLOB,
  metadata JSON   -- Oracle 21c+ native; 12c-19c dùng CLOB + CHECK (metadata IS JSON)
);
```

```sql
-- PL/pgSQL Function → PL/SQL Procedure
-- PostgreSQL:
CREATE OR REPLACE FUNCTION update_balance(p_cust_id INT, p_amount NUMERIC) RETURNS VOID AS $$
BEGIN
  UPDATE accounts SET balance = balance + p_amount WHERE customer_id = p_cust_id;
  IF NOT FOUND THEN RAISE EXCEPTION 'Customer not found'; END IF;
END;
$$ LANGUAGE plpgsql;

-- Oracle:
CREATE OR REPLACE PROCEDURE update_balance(p_cust_id IN NUMBER, p_amount IN NUMBER) IS
BEGIN
  UPDATE accounts SET balance = balance + p_amount WHERE customer_id = p_cust_id;
  IF SQL%ROWCOUNT = 0 THEN RAISE_APPLICATION_ERROR(-20001, 'Customer not found'); END IF;
  COMMIT;
END;
/
```

```
☐ Ghi vượt vài trăm nghìn record/giây, cần scale ngang?     → Cassandra/HDFS
☐ Trọng tâm tìm quan hệ nhiều bước giữa thực thể?           → Neo4j
```
